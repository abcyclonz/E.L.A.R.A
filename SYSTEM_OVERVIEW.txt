[2026-05-10]  Memory extraction overhaul — model upgrade, prompt rewrite, fixes
────────────────────────────────────────────────────────────────────────────────

UPGRADE — Extraction model  (agents/memory/app/extractor.py)
  • Local dev model bumped qwen2.5:3b → qwen2.5:7b via OLLAMA_MODEL env var.
    Production (RunPod) continues to use qwen2.5:32b — no code change needed there.
  • Root cause identified: 3b model could only extract one type of fact (location)
    regardless of message content, causing every utterance to be stored as
    user.location=<something>.

FIX — Extraction prompt rewrite  (agents/memory/app/extractor.py → EXTRACTION_PROMPT)
  • Previous prompt had a literal `"value": "Kerala"` in the example JSON; small
    models copied it verbatim for every input regardless of actual content.
    Changed to `"value": "<extracted_value_here>"` placeholder.
  • Complete rewrite with 7 diverse few-shot examples covering all claim types:
      A — name + birthplace (two STATE claims, importance 0.95, permanent)
      B — spouse bereavement (two STATE claims, importance 0.95, permanent)
      C — multi-entity family (four STATE claims across two children with locations)
      D — BELIEF type + hobby STATE (distinguishes subjective opinion vs fact)
      E — EVENT + relation + location (three claim types in one message)
      F — doctor + health condition (medical STATE claims)
      G — correction with corrects_entity (versioning / fact update)
  • BELIEF type clarified: only fires when speaker uses explicit opinion language
    ("I think", "I feel", "I believe", "I love", "I hate", "I trust").
  • LLM timeout raised 30s → 90s; max_tokens raised 500 → 1200 to accommodate
    multi-claim responses (e.g. a message that mentions two children generates 4 claims).
  • INTENT_PROMPT rewritten with explicit examples so "tell me everything about X"
    routes to HISTORY (not GENERAL), enabling full-profile retrieval.

FIX — BELIEF write fallback  (agents/memory/app/main.py)
  • LLM occasionally places the opinion subject in `entity` instead of
    `entity_or_event`. The write gate silently dropped these claims.
  • Fix: if `entity_or_event` is empty but `entity` is present, use `entity` as
    `entity_or_event` before writing to belief_memory.

NEW — Rigorous memory test suite  (test_memory_rigorous.py, 39 checks)
  • Covers: health check, short-term storage, grounding facts, family relations,
    belief layer, event layer, versioning/correction, deduplication, pronoun
    resolution, transient stability, multi-speaker isolation, salience scoring,
    episodic recall, world-knowledge filter, and intent classification.
  • Relation assertions scan both entity and value fields (sons stored as
    entity=David, attribute=relation_to_George, value=son — not value=David).
  • Belief assertions accept both belief_memory encoding and STATE opinion_* fallback.
  • All 39 checks pass against qwen2.5:7b local / qwen2.5:32b on RunPod.

[2026-05-10]  Proactive health monitoring — watch data thresholds + alert system
────────────────────────────────────────────────────────────────────────────────

NEW — Watch Data Health Monitor  (agents/elara/health_monitor.py)
  • Smartwatch readings (HR, temperature, battery) are now checked against
    safe-range thresholds every time the frontend posts to /watchdata.
  • Threshold rules (deterministic, no LLM):
      HR > 110 BPM      → heart rate too high (tachycardia concern)
      HR < 50 BPM       → heart rate too low  (bradycardia concern)
      Temp > 37.5°C     → possible fever
      Temp < 35.0°C     → possible hypothermia
      Battery < 15%     → watch needs charging (info-level, not health-critical)
  • On breach: /watchdata returns alert=true + elara_message (warm, Elara-style
    proactive question). Frontend reads the response and displays the message
    in the chat UI without the user having to say anything.
  • Per-issue, per-session 10-minute cooldown prevents repeat alerts for the
    same problem. Each issue type (hr_high, hr_low, temp_high, temp_low,
    battery_low) has its own independent cooldown timer — battery low can still
    fire even if hr_high is in cooldown.
  • Zero readings (hr=0, temp=0.0) are ignored — treated as sensor absent.
  • Multiple issues in one poll are combined into a single message: health
    alerts lead, info alerts (battery) trail, joined with "Also, ...".
  • Normal readings return {"status": "received", "alert": false} unchanged.

NEW — Watch Data API Route  (frontend/app/api/watchdata/route.ts)
  • Frontend Next.js route proxies POST /watchdata to BACKEND_URL (Elara :8002).
  • Accepts: session_id, hr, battery, steps, temp + auto-stamps timestamp.
  • Added by team PR (merged 2026-05-10). Health monitor backend built on top.

[2026-05-10]  Voice pipeline moved to cloud — Pi thin client, DB ownership fix, location fix
────────────────────────────────────────────────────────────────────────────────

ARCHITECTURE CHANGE — Voice processing fully moved to RunPod
  • Previously: Pi ran Silero VAD, Faster-Whisper STT, SpeechBrain speaker ID, and
    Kokoro TTS locally. Required the Pi to have 4+ GB RAM and all ML models.
  • Now: Pi is a thin audio terminal only.
      Pi sends: raw PCM int16 frames (16kHz, mono, 512-frame chunks) over WebSocket
      RunPod runs: VAD → STT → Speaker ID → Orchestrator → Elara → TTS
      RunPod sends: Kokoro TTS WAV back to Pi for playback
  • Pi mic is muted during TTS playback (threading.Event flag) to prevent echo.

NEW — Audio Gateway  (agents/orchestrator/app/audio_ws.py)
  • WebSocket endpoint at /ws/audio on the orchestrator (port 8001 Docker / 8003 native).
  • AudioPipeline singleton loaded in background daemon thread at startup (non-blocking
    so orchestrator health check passes before 2GB of models are downloaded).
  • Pipeline components loaded once and reused per connection:
      - Silero VAD (torch.hub, float32 normalized input)
      - Faster-Whisper "base.en" (CPU int8)
      - SpeechBrain ECAPA-TDNN (cosine similarity, threshold 0.25)
  • VAD accumulates speech frames; on silence timeout (0.8s) sends phrase to STT+Speaker.
  • Speaker embeddings persisted to /data/speaker_embeddings.json — survive restarts.
  • After orchestrator pipeline runs, calls Elara /tts for Kokoro synthesis (best quality,
    24kHz WAV). Sends WAV bytes back to Pi over the same WebSocket.
  • Max message size: 10MB (handles long TTS responses).

NEW — Pi Thin Client  (pi_client/)
  • Self-contained folder designed to be copied to Pi and run with: bash run.sh
  • audio_client.py: PyAudio mic → WebSocket → RunPod, receive WAV → PyAudio playback
  • requirements.txt: pyaudio, websockets, python-dotenv (no ML dependencies)
  • .env.example: template with ORCHESTRATOR_WS_URL pointing to RunPod proxy URL
  • run.sh: installs portaudio, creates venv, installs deps, starts client
  • Connection URL format: ws://<pod-id>-8001.proxy.runpod.net/ws/audio

ORCHESTRATOR CHANGES
  • Added WebSocket route @app.websocket("/ws/audio")
  • Added torch, torchaudio, faster-whisper, speechbrain, websockets to requirements.txt
  • Added libsndfile1 ffmpeg system deps to Dockerfile
  • Added speaker_data Docker volume for embedding persistence

BUG FIX — Memory completely non-functional (CRITICAL — broke all memory storage)
  • Symptom: 0 rows stored in state_memory after many "store" turns.
    Memory agent logs showed: "column 'importance' does not exist" and
    "InsufficientPrivilege: must be owner of table state_memory".
  • Root cause: init.sql creates all tables owned by the postgres superuser.
    Memory agent connects as memory_user (granted ALL PRIVILEGES, but not OWNER).
    PostgreSQL requires table OWNERSHIP — not just privileges — to run ALTER TABLE
    or CREATE INDEX. All 4 startup migrations failed silently:
      - _SPEAKER_ID_MIGRATION (adds speaker_id column)
      - _PRIORITY_MIGRATION   (adds importance, stability, access_count)
      - _GROUNDING_MIGRATION  (adds is_grounding)
      - _EPISODES_DDL         (creates episodes table)
    Result: columns never added → every INSERT failed → 0 memories stored.
  • Fix applied on live pod: ran as postgres superuser:
      ALTER TABLE state_memory    OWNER TO memory_user;
      ALTER TABLE belief_memory   OWNER TO memory_user;
      ALTER TABLE event_memory    OWNER TO memory_user;
      ALTER TABLE episodes        OWNER TO memory_user;
      ALTER TABLE memory_logs     OWNER TO memory_user;
      ALTER TABLE topic_frequency OWNER TO memory_user;
    Restarted memory agent → all 4 migrations ran → memory storage restored.
  • PERMANENT FIX STILL NEEDED in start.sh (see KNOWN GAPS below).
    Every fresh pod will have broken memory until start.sh is updated.

BUG FIX — Location always returning RunPod datacenter city (Prague/Frankfurt)
  • Symptom: Restaurant searches returned Prague results even when user said
    "I am in Trivandrum". Elara confirmed "I understand you're in Trivandrum"
    but then searched the wrong city anyway.
  • Root cause: handle_input() called ipinfo.io first with no timeout. RunPod
    server IP geolocates to a European datacenter. Browser GPS in
    req.metadata["location"] was being silently discarded.
  • Fix: Changed location priority order in handle_input():
      1. req.metadata["location"]     — browser GPS (most accurate)
      2. _location_from_grounding()   — extracted from memory grounding facts
      3. ipinfo.io fallback           — only if above both empty, 2s timeout
    This means browser-provided GPS always wins over server IP geolocation.

[2026-05-09]  Vision channel — Eye + Perception Monitor + Perception Learner
────────────────────────────────────────────────────────────────────────────────

NEW — Eye  (Face_login_Elara-master/, Raspberry Pi 5)
  • Added the physical "eye" of the system: a Raspberry Pi 5 running a FastAPI
    camera service on port 8765.
  • Face detection at 20fps via OpenCV Haar cascade; tracked face drives
    pan-tilt servo camera via PID controller → ESP32 over USB serial (115200 baud).
  • dlib face encoding (every 3s) confirms identity against registered users.
  • Face encodings stored in faces/db.json; registered via browser UI at /.
  • Two modes: Pi mode (picamera2) and laptop mode (browser-injected frames).
  • Key endpoint: GET /frames/event — returns current frame (base64), bounding
    box, identified user name, and face position as a single JSON payload.
  • Falls back to servo simulation if no ESP32 is connected.

NEW — Perception Monitor  (Face_login_Elara-master/monitor.py, runs on RunPod)
  • Polls GET /frames/event from the Pi every MONITOR_PERIOD_S seconds (default 60s).
  • Three-stage perception analysis pipeline on each frame:
      1. HSEmotion (EfficientNet-B0, ONNX): face crop → 8-class emotion scores
         Labels: anger, contempt, disgust, fear, happiness, neutral, sadness, surprise
      2. Moondream VLM (Ollama): full frame → natural language scene description
         (describes surroundings only — not the user's face or expression)
      3. Mistral LLM (Ollama): emotion + scene + previous snapshot → structured JSON
         including emotion_affected_by_scene (bool), reason, summary
  • Smart deduplication before writing: only records a row if emotion changed,
    affected flag flipped, or >50% of scene subjects swapped (Jaccard < 0.5).
    Prevents thousands of identical rows per day.
  • Writes to timeline.db (SQLite) in the perception_data Docker volume.
  • Only processes frames where an identified (named) user is present — skips Unknown.

NEW — Perception Learner  (agents/perception_learner/, port 8012)
  • Passive background agent — completely decoupled from the live conversation.
    DOES NOT interact with Elara, Orchestrator, or the NLP pipeline.
    SEPARATE from Elara's learning system (which handles conversation preferences).
  • What it does: fuses what the camera SAW with what the user SAID in conversations
    to generate richer episodic memories that neither source alone would produce.
  • Poll loop (every POLL_INTERVAL_S seconds, default 600):
      1. Reads new rows from timeline.db since last processed snapshot ID.
      2. For each new snapshot: calls memory_agent:8000/retrieve with the
         user + scene/subjects as query context.
      3. If no relevant memory found → SKIP (nothing to cross-reference).
      4. Sends snapshot + memory context to Mistral (Ollama) with cross-modal
         reasoning prompt. LLM returns one grounded inference sentence or SKIP.
      5. If inference generated: calls memory_agent:8000/process → stored as
         an EVENT memory. Indistinguishable from conversation-derived events;
         retrieved naturally by the Orchestrator on future turns.
  • Example inference: memory has "user's son is tall" + camera sees "tall person
    holding a basketball" + user is happy → stored: "User appeared happy while
    their tall son was present in the scene holding a basketball."
  • State tracking: own SQLite (learner_state.db) records every processed
    snapshot ID + the inference text (null if SKIP). Survives container restarts.
  • Debug endpoints:
      POST /debug/inject_snapshot — write a test row into timeline.db directly
      POST /debug/trigger         — force one immediate poll cycle, return results
  • Test coverage: Scenario 10 in analysis_test.py exercises the full flow —
    injects a snapshot for George (sad near roses + photographs), triggers the
    learner, verifies the inference connected to his known grief over his late wife.

DOCKER COMPOSE CHANGES
  • Added perception_monitor service (builds from Face_login_Elara-master/Dockerfile.monitor)
  • Added perception_learner service (builds from agents/perception_learner/)
  • Added perception_data volume (shared between monitor and learner for timeline.db)
  • Added learner_state volume (perception_learner's own processed-ID tracker)

ARCHITECTURAL NOTE — LLM UPGRADE PLANNED
  • The majority of routing short-circuits and grief filter complexity exists
    because Mistral 7B cannot reliably follow multi-conditional system prompt
    instructions. The model ignores "DO NOT mention" boundaries and misroutes
    messages that a larger model handles correctly from the prompt alone.
  • PLAN: upgrade the router and conversation LLM to Llama 3 70B via Groq
    (or equivalent capable model). This would collapse most of the routing
    short-circuit layer and make the grief sensitive-block instruction
    actually reliable — reducing code complexity and improving reply quality.
  • Current short-circuit layer remains as a safety net even after upgrade.

BUG FIX — Deceased relative facts leaking into normal context  (orchestrator/app/agents.py)
  • Root cause: _format_grounding() only checked the *attribute* of each fact for
    grief markers. Facts like wife.skill=make cupcakes, wife.product=cupcakes,
    wife.job=cupcake_maker, partner.relationship_duration=48 years, and
    deceased_relative.preference=roses all landed in Elara's normal background
    block, causing her to spontaneously connect roses/cupcakes → deceased wife
    even on a plain greeting.
  • Fix: two-pass classification in _format_grounding():
    1. First pass identifies all deceased entities by attribute, value, or
       entity name (e.g. "deceased_relative.*" caught by name).
    2. Spouse linkage: if any spouse-type entity (wife/husband/partner/spouse)
       is deceased, ALL spouse-type entities are marked deceased.
    3. Second pass routes EVERY fact about a deceased entity to the sensitive
       "[Sensitive background — DO NOT mention unless user raises this topic]"
       block, regardless of attribute.
  • Added _SPOUSE_TERMS frozenset for the spouse linkage logic.

BUG FIX — Grief post-processing filter too narrow  (elara/conversation_agent/adapter.py)
  • _GRIEF_SENTENCE_RE did not catch indirect grief references:
    "missing her/him", "beloved mother/wife", "linger in your heart",
    "thinking about her recently", "she's gone", "still remember her".
  • LLM was generating these softer phrasings to bypass the original patterns
    while still referring to the deceased — including hallucinating "Mother's Day"
    from the May date combined with deceased wife facts.
  • Expanded _GRIEF_SENTENCE_RE with six additional sub-patterns to catch
    these indirect references.

BUG FIX — Style request routed to STORE_MEMORY  (orchestrator/app/main.py)
  • "just speak normally pk?" matched no short-circuit and was routed by the
    LLM to STORE_MEMORY, extracting a spurious user.name=unknown fact at conf 1.0
    and tagging retrieved facts with emotion=frustrated.
  • Added _STYLE_FEEDBACK_RE short-circuit before the LLM router:
    casual style requests ("speak normally", "just be natural", "stop being so
    formal", etc.) → DIRECT_CHAT, memory untouched.

WHAT IS ELARA?
--------------
ELARA is a real-time, affect-adaptive AI companion designed for elderly users.
It listens through a microphone, understands who is speaking, remembers things
across conversations, learns how to communicate based on the user's emotional
state, and can search the web, set reminders, and manage calendar events — all
through natural voice conversation.

ELARA also has a physical eye: a Raspberry Pi camera that watches, identifies
the user, reads their emotion, understands the scene around them, and uses that
to enrich memory with insights that conversation alone would never produce.

Two parallel channels feed a shared memory store:

  VOICE CHANNEL (real-time):
    Microphone
      → VAD (silence detection)
      → STT (speech-to-text) + Speaker ID (who is talking)
      → Orchestrator (routes the message)
      → Memory Agent (stores / retrieves personal facts)
      → Tool Servers (web search, reminders, calendar)
      → Elara Conversation Agent (generates reply)
      → TTS (text-to-speech output)

  VISION CHANNEL (passive, background — never blocks conversation):
    Raspberry Pi camera
      → Face detection + pan-tilt tracking (Eye service, Pi)
      → Identity confirmed → frame sent to RunPod
      → Perception Monitor (emotion + scene analysis via Ollama)
      → timeline.db (SQLite, shared Docker volume)
      → Perception Learner (cross-modal reasoning every 10 min)
      → Memory Agent (stores grounded inferences as EVENT memories)
      ↓
    Same memory store the Orchestrator reads on every voice turn

────────────────────────────────────────────────────────────────────────────────
1. VOICE PIPELINE  (MIC/)
────────────────────────────────────────────────────────────────────────────────

  • Microphone capture via PyAudio (16 kHz, mono, int16, 512-frame chunks)
  • Silero VAD (Voice Activity Detection) — filters silence, triggers on speech
  • Faster-Whisper STT (base.en model, CPU int8) — transcribes speech to text
  • SpeechBrain ECAPA-TDNN speaker identification — cosine similarity, threshold 0.25
    Auto-registers new speakers as User_1, User_2, etc.
  • Silence timeout (0.8s) marks end of phrase; min phrase length 0.5s
  • STT and speaker ID run in parallel threads for low latency


────────────────────────────────────────────────────────────────────────────────
2. MEMORY SYSTEM  (agents/memory/)
────────────────────────────────────────────────────────────────────────────────

  Three memory layers in PostgreSQL:

    STATE   — mutable facts about the user (name, location, job, mood)
              Versioned: each update closes the old row (valid_to) and opens a new one
    BELIEF  — subjective opinions and feelings ("I think...", "I feel...")
              Also versioned with history
    EVENT   — immutable things that happened (achievements, incidents, appointments)
              768D embeddings (nomic-embed-text) for semantic search

  Every claim carries:
    • importance  (0–1): how fundamental is this fact to understanding the person
    • stability   (permanent | stable | transient): how long it should persist

  Salience scoring (used to rank what to show Elara):
    salience = importance × 0.40 + recency × 0.40 + frequency × 0.20
    Recency uses half-life decay:
      permanent = 3650 days (10 years) — name, deceased relatives, birthplace
      stable    = 365 days  (1 year)  — job, home, long-term relationships
      transient = 14 days   (2 weeks) — mood, today's plan, passing remark
    Facts below salience 0.10 are excluded from normal retrieval (soft forgetting)

  LLM claim extraction:
    Ollama (Mistral 7B) reads each user message and extracts typed claims
    with importance and stability values. Rates bereavement, serious illness,
    and key relationships at 0.9+ importance / permanent stability.

  Episodic memory:
    Every conversation turn is stored verbatim with a 768D embedding.
    Semantic search over episodes for "remember when..." style recall.

  LLM relevance reranking:
    After salience filtering, a single Ollama call scores each candidate 0–10.
    Final score = salience × 0.5 + LLM relevance × 0.5.

  GROUNDING LAYER  (built recently):
    High-importance permanent facts (importance ≥ 0.85, stability = permanent)
    are auto-flagged as "grounding" in the database.
    Examples: mother passed away, user has two sons, user was born in Kerala.
    Grounding facts are fetched on EVERY turn (no salience decay, no query needed)
    and prepended to Elara's prompt as a permanent background block.
    This means Elara always "knows" these things even when talking about
    completely unrelated topics like coffee shops or the weather.
    Existing facts are backfilled automatically on startup.


────────────────────────────────────────────────────────────────────────────────
3. ORCHESTRATOR / ROUTER  (agents/orchestrator/)
────────────────────────────────────────────────────────────────────────────────

  5-way LLM router decides what to do with each user message:

    STORE_MEMORY       — user is stating a personal fact → store to memory
    RETRIEVE_MEMORY    — user is asking about personal history → retrieve from memory
    STORE_AND_RETRIEVE — user is correcting a stored fact → update + retrieve
    USE_TOOL           — user needs web search, reminder, or calendar
    DIRECT_CHAT        — greeting, small talk, Elara-directed question → skip memory

  Pre-routing short-circuits (bypass the LLM router entirely):
    • Single-word affirmations (ok, yes, sure, yeah...) → always DIRECT_CHAT
    • Gratitude phrases (thanks, thank you, cheers) → canned "You're welcome!" reply

  Context-aware routing  (built recently):
    The last 4 turns of conversation are included in the router prompt so it
    understands corrections ("oh sorry I meant restaurants") and follow-ups.

  Correction / clarification routing  (built recently):
    Rule (d): if the user is correcting a prior tool request, the router
    re-routes to USE_TOOL with the same tool (e.g. after a hotel search,
    "I meant restaurants" → new web_search, not STORE_MEMORY).

  Implicit nearby-search detection  (built recently):
    Rule (e): "I want a coffee so bad", "I need a taxi" →
    detected as nearby-search intent → USE_TOOL | web_search.
    Distinguished from personal statements: "I want to sleep" → STORE_MEMORY.
    Key rule: want/need [tangible NOUN] = search; want to [VERB] = memory.

  User-directed vs self-directed search distinction  (built recently):
    "Can you search up nearby me" → USE_TOOL (Elara is asked to search)
    "I need to search up my friend tomorrow" → STORE_MEMORY (user's own plan)

  DIRECT_CHAT detection improved  (built recently):
    Questions directed at Elara ("how have you been", "how are you doing",
    "what do you think") are correctly classified as DIRECT_CHAT instead of
    being mistakenly stored as memory.

  Context-aware tool parameter extraction  (built recently):
    When the user's message is vague ("search up nearby me"), the last 4
    conversation turns are included in the extraction prompt so the LLM can
    infer the actual search subject from context (e.g. "teddy bear stores
    near me" from a prior discussion about buying a teddy bear for Gini).

  Style frustration detection:
    A quick Ollama call detects if the user is frustrated with Elara's
    communication style (too long, too wordy, too formal). Injects
    emotion=frustrated before routing.

  Conversation summarization:
    Every 5 turns, the last N turns are summarised by Ollama and stored
    as an EVENT in memory so long-term context is not lost.

  Per-speaker session state:
    Each speaker's Elara session (history, personality, bandit state) is
    stored in Redis and survives container restarts.

  Authentication:
    POST /auth/signup — creates account, seeds profile facts into memory
    POST /auth/login  — returns JWT token
    POST /chat        — token-gated endpoint for web/app clients

  Grounding facts on every turn  (built recently):
    /grounding/{speaker_id} is called before routing. The biographical
    background is passed to Elara regardless of router decision.


────────────────────────────────────────────────────────────────────────────────
4. ELARA CONVERSATION AGENT  (agents/elara/)
────────────────────────────────────────────────────────────────────────────────

  LLM backend: Mistral 7B via Ollama (default). Groq also supported.
  TTS: Kokoro (local) or Edge TTS (cloud).

  Personality system (9D PersonalityVector):
    Dimensions: warmth, humor, playfulness, formality, verbosity, pace,
                clarity, patience, assertiveness
    All continuous [0, 1]. Three-layer update each turn:
      1. Personal Profile (P): EMA of per-user baseline, updated from bandit
      2. Session Bandit (S): LinUCB selects which dimension to nudge ±0.10
      3. Context Gate (C): affect-based caps/floors
         e.g. sad → humor capped at 0.15, warmth floored at 0.75
    Style directive generated from PersonalityVector and injected into prompt.
    Max tokens per pace: slow=160, normal=100, fast=60.

  Affect classification:
    5 states: CALM | FRUSTRATED | CONFUSED | SAD | DISENGAGED
    NLP signals extracted by structured Ollama call each turn:
      sentiment, repetition, confusion, sadness, humor_receptive,
      wants_shorter, wants_simpler, explicit_positive, explicit_negative,
      personality_hints
    Short messages (≤2 words) skip the LLM call.
    Falls back to VADER + keyword lists if Ollama is unreachable.
    Escalation smoother: 4 rules prevent sudden affect jumps.
    Rule R4: prevents "Hi" from being classified as disengaged.

  LinUCB contextual bandit:
    19 actions (DO_NOTHING + INCREASE/DECREASE for each of 9 personality dims)
    14D feature vector: 5D one-hot affect + 9D PersonalityVector
    Discount factor γ=0.95, exploration coefficient α=0.8
    Matrices persisted per-user to Docker volume.
    Old 7D matrices auto-reinitialized on shape mismatch.

  Distress watchdog:
    7 consecutive non-calm turns → caregiver_alert: true
    Sends email via Gmail SMTP (requires GMAIL_APP_PASSWORD env var).
    Alert sent to ALERT_TO_EMAIL (comma-separated caregiver addresses).

  Greeting reset:
    Greetings ("hey", "hi", "good morning"...) clear conversation history
    AND the bandit's affect_window so old emotional context never bleeds
    into a new session.

  Post-processing:
    Leading "Hello [Name]" greetings stripped after the first turn.

  CURIOSITY / PROACTIVE SYSTEM  (agents/elara/curiosity_agent/)  [new]:

    Elara now proactively brings up things she's curious about — people,
    health, hobbies, past events — weaving them naturally into replies.

    CuriosityItem (schemas.py):
      Each item has: question, topic_triggers, suppress_if_topics,
      suppress_if_affects, emotional_sensitivity (0–1), priority, ask_count.

    Generator (generator.py):
      Every 10 turns, a passive Ollama call reads the full memory snapshot
      and last 6 conversation turns, then produces 6–8 natural questions.
      Examples it might generate:
        "Hey, how's David doing these days?"
        "Did your knee feel any better this week?"
        "You love cupcakes — did you find a good bakery nearby?"

    Injector (injector.py) — decides when to ask:
      • Topic trigger:   if current message contains a trigger word, score +0.45
                         (hotel message → cupcake question becomes timely)
      • Affect gate:     sad or frustrated → no proactive questions at all
      • Sensitivity gate: high-sensitivity items (≥ 0.7) only when affect = calm
      • Topic suppression: suppress_if_topics words in message → blocked
                           (flowers question suppressed when user mentions funeral)
      • LLM timing veto:  for sensitivity ≥ 0.6, a fast Ollama call rates timing
                           0–10; blocked if score < 6 (catches nuanced wrong moments
                           the rule layer misses — e.g. flowers at a funeral)
      • Probability gate: base 28%, up to 65% on strong trigger, scaled by
                          proactive_receptiveness

    Feedback loop:
      proactive_receptiveness (EMA, starts 0.7) — learned per session:
        User responds with disengaged/frustrated → −0.25
        User responds calm + positive sentiment  → +0.10
        Below 0.15 → proactive goes silent for this session
      Each question asked at most 3 times; min 4 turns between questions.

    Integration:
      Proactive question injected as a [Organic curiosity] hint into Elara's
      system prompt — she weaves it in naturally rather than appending it raw.

5. WATCH DATA HEALTH MONITOR  (agents/elara/health_monitor.py)
────────────────────────────────────────────────────────────────────────────────

  Endpoint: POST /watchdata on Elara (:8002)
  Called by: frontend/app/api/watchdata/route.ts (Next.js proxy route)
  Fields accepted: session_id, hr (BPM), battery (%), steps, temp (°C)

  How it works:
    1. Frontend simulation posts watch readings whenever they update.
    2. health_monitor.check_watch_data() runs deterministic threshold checks.
    3. Each issue is filtered through a per-session, per-issue 10-minute
       cooldown so the user is only notified once per sustained problem.
    4. If new issues remain after cooldown filter:
         build_proactive_message() assembles a warm Elara-style message.
         /watchdata returns: {alert: true, elara_message: "...", issues: [...]}
    5. Frontend detects alert=true and displays elara_message in the chat UI
       as a proactive message from Elara — no user action needed.
    6. Normal readings return {alert: false} — no disruption to the user.

  Thresholds:
    hr_high     HR > 110 BPM     health  "heart rate seems quite high — X BPM"
    hr_low      HR < 50 BPM      health  "heart rate looks a little low at X BPM"
    temp_high   Temp > 37.5°C    health  "temperature is reading X°C, a bit warm"
    temp_low    Temp < 35.0°C    health  "temperature is on the lower side — X°C"
    battery_low Battery < 15%    info    "watch battery running low at X%"

  Cooldown: 10 minutes per issue per session (ALERT_COOLDOWN in health_monitor.py)
  Zero sensor values (hr=0, temp=0.0) are skipped — treated as sensor absent.

8. VISION PIPELINE  (Face_login_Elara-master/ + agents/perception_learner/)
────────────────────────────────────────────────────────────────────────────────

  7a. EYE SERVICE  (Raspberry Pi 5, port 8765)

    • FastAPI server — camera feed, face registration/login, tracking status.
    • Face registration: browser UI captures 3+ frames → dlib extracts 128D
      face encodings → stored in faces/db.json.
    • Face login: incoming frame matched against db.json; on match, tracker is
      told who is present (tracker.set_identified_person(name)).
    • FaceTracker runs two daemon threads:
        Main loop (20fps): Haar cascade → detect largest face → compute PID
          error (offset from frame centre) → send angle delta to ESP32 servo.
        Recognition loop (every 3s): dlib face encoding → cosine match against
          identified user → update identified_present flag.
    • PID controller: discrete P+I+D with anti-windup + deadband (30px).
      Pan/tilt servo limits: 30°–150° each (90° = centre).
    • ESP32 firmware: receives "P<pan> T<tilt>\n" over serial → PWM servo.
      Falls back to simulate mode (tracks angle state only) if no ESP32.
    • Key endpoints:
        GET /frames/event  — JSON: frame_b64, person, box, position,
                             identified_name, identified_present
        GET /track/stream  — MJPEG live feed with HUD overlay
        POST /login        — match face → returns name + confidence
        POST /register     — store new face encodings

  7b. PERCEPTION MONITOR  (RunPod Docker service, perception_data volume)

    • Pulls GET /frames/event from Pi every MONITOR_PERIOD_S seconds.
    • Only processes frames where identified_present = True and user ≠ Unknown.
    • Three-stage pipeline:
        Stage 1 — HSEmotion (enet_b0_8_best_afew, ONNX):
          Crops face from bounding box (±20px padding) or centre fallback.
          Outputs dominant emotion + 8-class probability distribution.
        Stage 2 — Moondream VLM (Ollama):
          Encodes full frame as base64 JPEG; prompts model to describe only
          surroundings (objects, people, environment) — not the user's face.
        Stage 3 — Mistral LLM (Ollama):
          Combines emotion scores + scene description + previous snapshot
          → structured JSON: emotion, confidence, emotion_scores,
            scene_description, subjects (up to 5), emotion_affected_by_scene,
            reason, summary.
    • Deduplication: writes to timeline.db only if emotion changed, affected
      flag flipped, or Jaccard similarity of subjects < 0.5 (>50% changed).
    • timeline.db lives in perception_data Docker volume at /app/faces/timeline.db.

  7c. PERCEPTION LEARNER  (agents/perception_learner/, port 8012)

    • Entirely passive — zero interaction with live conversation pipeline.
      Separate from Elara's preference-learning system.
    • Goal: generate memories that require BOTH vision (what was seen) AND
      conversation (what is known) to produce — neither alone is enough.
    • Poll cycle (every POLL_INTERVAL_S seconds, default 600s):
        1. Read new rows from timeline.db (id > last_processed_id).
        2. For each snapshot: call memory_agent /retrieve with user + scene
           subjects as query → get relevant facts, beliefs, recent events.
        3. If no memory context found → mark SKIP, move on.
        4. Build cross-modal reasoning prompt → send to Mistral (Ollama).
           LLM returns one grounded inference sentence or the word SKIP.
        5. If inference returned: call memory_agent /process with the
           inference text → stored as EVENT memory with metadata:
           {source: "perception_learner", snapshot_id: N, snapshot_ts: T}
    • State DB (learner_state.db in learner_state volume):
        processed table: snapshot_id | processed_at | inference (nullable)
        Guarantees each snapshot is reasoned over exactly once.
    • Graceful degradation: if timeline.db doesn't exist yet (monitor not
      started), learner silently waits; if memory_agent unreachable, SKIP.

                          e.g. http://192.168.1.42:8765
  MONITOR_PERIOD_S      — how often perception_monitor pulls a frame (default 60)
  POLL_INTERVAL_S       — how often perception_learner checks for new snapshots (default 600)

================================================================================
  KNOWN GAPS / FUTURE WORK
================================================================================

  • Speaker ID persistence: known_speakers is in-memory, lost on restart
  • Location awareness: frontend requests browser geolocation → Nominatim
    reverse geocode → city string sent with every message; memory-stored
    location used as fallback. Web searches are now location-specific.
  • Bandit cold start: first ~20 turns are exploration; no population warm-start
  • LLM quality ceiling: Mistral 7B occasionally hallucinates mild emotional
    context and gives unsolicited advice; Llama 3 70B via Groq would improve this
  • Health monitor tool: IMPLEMENTED — watch data thresholds active via
    /watchdata endpoint on Elara; proactive alert returned to frontend on breach
  • Proactive check-ins (in-conversation): IMPLEMENTED via curiosity agent.
    Scheduled out-of-turn initiation ("Good morning", medication reminders)
    still not implemented — would require APScheduler + server-push to frontend
  • Caregiver email: currently only fires on distress watchdog; no free-form
    email composition on behalf of the user
  • Eye face encodings: faces/db.json on the Pi is not backed up — re-registration
    needed if Pi is wiped or reimaged
  • Perception learner bulk catch-up: if many snapshots accumulate before the
    learner first runs, all are processed in one burst with no rate limiting
  • Cross-user perception: perception_learner only reasons per identified user;
    no cross-user inferences are ever made (intentional — privacy by design)
